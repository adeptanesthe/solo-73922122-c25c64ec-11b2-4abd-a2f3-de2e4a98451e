# 唤醒词缺报核对（wakeup-audit）

设备唤醒日志缺失一段时，用同期留存的模型分数重建缺报区间内的触发帧；
另提供**双音箱试跑**：两台音箱同时听见唤醒词时，按窗口仲裁只让一台应答。

## 规则一：单音箱缺报核对

- 帧号从 0 起；缺报区间包含首尾；分数为整数，最多 200000 帧。
- 未处于冷却的帧，分数达到阈值即触发；触发后接下来 `cooldown`（0～2000）帧冷却。
- 录制开始时可能仍在冷却，剩余帧数 `r ∈ [0, cooldown]`，每种 r 是一种"解释"。
- 缺报期间照常触发和冷却；**缺报区间外**有触发的帧必须**恰好**是回执列出的帧
  （区间外多出的触发、回执帧未触发都会否决该解释；区间内回执帧同样必须真实触发）。
- 缺报区间内：
  - **补记**：所有一致解释都触发的帧（含区间内已回执的帧，状态标 `received`）。
  - **待核**：只有部分一致解释触发的帧。
  - 无任何一致解释 → **冲突**，补记列表留空，并列出每种 r 的否决原因。

### 算法（不为每种初始冷却逐帧重扫分数）

1. 一次 O(N) 倒序扫描构造 `next_cross[i]`：从帧 i 起第一个达阈帧。
2. 把"下一可触发帧 s"沿函数链 `s → next_cross[s] → s + cooldown + 1 → …` 记忆化，
   所有 r 的链共享后缀；全部链总长度 O(N + cooldown)，20 万帧实测约 0.2～0.3 秒。
3. 对每种解释只做链上序列与回执的集合核对，再求区间内触发集的交集/并集差。

## 规则二：双音箱试跑（分块追加，流式仲裁）

两台音箱各自配置阈值与冷却帧数（0～2000）以及等待帧数 `W`（0～50），分数按块追加：

- 两路分数**对齐、同标度的整数**；每块注明起始帧，首块从 0 开始，后续须接续本路帧号。
- 每路最多 200000 帧；任一路最多领先 4096 帧；任一约束违反则**整块退回**，会话状态不变。
- 两台起初都可触发。只在两路都已收到的共同帧上推进：
  1. 从当前位置找任一台"未冷却且达阈"的首帧作为窗首，纳入窗首及之后 `W` 帧；
  2. 窗末两路都收到后才结算：从窗内未冷却且达阈的候选中取**分数最高**者，
     同分取**较早帧**，再同分取**一号音箱**；
  3. 胜者在窗末帧应答，从下一帧起冷却；另一台**沿用原来的冷却进度**；
  4. 下一轮从窗末后一帧开始。
- 两路**等长**才允许结束回放；未满的末窗按最后一帧结算。
  结束失败可继续追加；结束成功后拒收一切新块。
- 每次追加都即时返回已确定的应答（应答音箱 / 获选帧 / 应答帧）；
  内部 `frontier` 单调递增，每个共同帧只处理一次，**不重扫已处理的帧**。

## 运行

```bash
docker compose up --build
# 打开 http://localhost:8000
# 单音箱核对在"单音箱缺报核对"页；双音箱仲裁在"双音箱试跑"页
```

页面支持粘贴或从 `.txt/.csv` 文件导入分数（空白/逗号/换行分隔），
重新核对会自动撤下旧结论与旧补记下载（旧链接再访问返回 HTTP 410）。

## 接口

单音箱：

- `POST /api/check`：提交核对，返回结论、补记、待核或冲突否决原因。
- `GET /api/results/{id}/backfill.csv`：下载最近一次核对的补记 CSV
  （UTF-8 BOM，列：frame, score, status；冲突态 409，失效链接 410）。

双音箱试跑：

- `POST /api/dual/sessions`：用两台各自的阈值/冷却与 W 创建试跑会话。
- `POST /api/dual/sessions/{id}/blocks`：追加一块分数
  （`channel` 1/2、`start_frame`、`block` 整数数组），返回最新快照与本次新确定的应答；
  校验失败返回 400 且整块退回。
- `POST /api/dual/sessions/{id}/finish`：等长结束并结算末窗；不等长返回 400。
- `GET /api/dual/sessions/{id}`：查询当前快照。
- `GET /api/health`、`GET /api/limits`（含双音箱各项上限）。
